# Сервис назначения ревьюеров для Pull Request'ов

---

## Быстрый запуск

### Шаг 1: Запуск проекта

Проект запускается одной командой. Ничего настраивать не нужно — все переменные имеют значения по умолчанию:

```bash
make docker-up
```

Или напрямую через Docker Compose:

```bash
docker-compose up -d
```

-   Запускается PostgreSQL 16
-   Автоматически применяются миграции БД
-   Собирается и запускается API сервис
-   Сервис становится доступен на `http://localhost:8080`

### Шаг 2: Проверка работоспособности

Проверьте, что сервис запустился и работает:

```bash
curl http://localhost:8080/health
```

**Ожидаемый ответ:** `{"status":"ok"}`

Если видите этот ответ — проект работает корректно

### Шаг 3: Тестирование API

Попробуйте основные операции:

```bash
# 1. Создать команду
curl -X POST http://localhost:8080/team/add \
  -H "Content-Type: application/json" \
  -d '{
    "team_name": "backend",
    "members": [
      {"user_id": "u1", "username": "Alice", "is_active": true},
      {"user_id": "u2", "username": "Bob", "is_active": true}
    ]
  }'

# 2. Создать Pull Request
curl -X POST http://localhost:8080/pullRequest/create \
  -H "Content-Type: application/json" \
  -d '{
    "pull_request_id": "pr-1",
    "pull_request_name": "Test PR",
    "author_id": "u1"
  }'

# 3. Проверить статистику
curl http://localhost:8080/stats
```

### Шаг 4: Запуск тестов

Проект содержит несколько типов тестов. Используйте команды из Makefile:

**Все тесты(кроме интеграционных тестов repository):**

```bash
make test
```

**Только юнит-тесты:**

```bash
make test-unit
```

**Интеграционные тесты handler:**

```bash
make test-handler
```

**Интеграционные тесты repository:**

```bash
make test-repository
```

**E2E тесты:**

```bash
make e2e-test
```

### Шаг 5: Остановка проекта

```bash
make docker-down
```

Для полной очистки (включая данные БД):

```bash
make docker-down-clean
```

## API Endpoints

### Teams

-   `POST /team/add` - Создать команду с участниками
-   `GET /team/get?team_name=<name>` - Получить команду

### Users

-   `POST /users/setIsActive` - Установить флаг активности пользователя
-   `GET /users/getReview?user_id=<id>` - Получить PR'ы, где пользователь назначен ревьювером

### Pull Requests

-   `POST /pullRequest/create` - Создать PR и автоматически назначить ревьюверов
-   `POST /pullRequest/merge` - Пометить PR как MERGED
-   `POST /pullRequest/reassign` - Переназначить ревьювера

### Health & Stats

-   `GET /health` - Проверка здоровья сервиса (включает проверку подключения к БД)
-   `GET /stats` - Статистика по назначениям

## Нагрузочное тестирование

Для проведения нагрузочного тестирования используйте:

```bash
make loadtest
```

Проверяет соответствие требованиям: RPS 5, время ответа p95/p99 < 300ms, успешность > 99.9%. Подробности: `docs/LOADTEST.md`

## Вопросы и решения

В процессе разработки возникли вопросы, ответы на которые не были явно описаны в задании. Ниже представлены принятые решения и их обоснование.

### 1. Обработка случаев, когда нет кандидатов для назначения

**Вопрос:** Что делать, если в команде автора нет активных ревьюверов (кроме самого автора)?

**Решение:** PR создаётся с пустым списком ревьюверов. Это позволяет:

-   Не блокировать создание PR
-   Назначить ревьюверов позже через `reassign`
-   Сохранить целостность данных

**Обоснование:** В реальных системах команда может быть небольшой или участники могут быть временно неактивны. Лучше иметь PR без ревьюверов, чем блокировать создание PR.

### 2. Массовая деактивация пользователей

**Вопрос:** Как реализовать массовую деактивацию с переназначением PR (дополнительное задание)?

**Решение:**

-   Используется батч-обновление через транзакцию (`BulkUpdatePRReviewers`)
-   Сначала деактивируются пользователи
-   Затем находятся все открытые PR с этими ревьюверами
-   Для каждого PR находится команда заменяемого ревьювера и выбирается новый активный участник
-   Все обновления выполняются в одной транзакции

**Обоснование:** батч-обновление позволяет уложиться в требования производительности (100 мс для средних объёмов данных) и обеспечить атомарность операций.
